## Objective and decisions

Accepted delivery: [TPU7x qualification summary](../reports/google_tpu/tpu7x/qualification-summary.md).
Native smoke, all 184 portable cases, compute/transfer/Pallas timing controls,
the 18-case collective sweep, independent environment replay and artifact checks
passed. Fifteen accepted reports are curated; three diagnostic runs are retained.

Add a TPU backend spanning multiple architecture generations, runtime versions,
and deployed instances. The supplied machine is the first qualification instance.
Add `amora tpu` with capability discovery, TPU-specific probes, immutable
measurement artifacts, and execution of the existing portable workloads. Use
**JAX + PJRT/libtpu** for the first runtime and **Pallas/Mosaic TPU** for probes
that need explicit tiles, memory spaces, or asynchronous transfers. Qualify
single-device execution, then collectives on each instance's addressable mesh.

The first useful delivery is a reproducible runtime snapshot, correct compiled
workloads, synchronized measurements, and matrix/vector/host-transfer curves.
Add controlled-memory curves on instances with a qualified implementation.
Profiler traces and Pallas kernels progressively strengthen those observations
when qualified on the target generation/runtime. PyTorch/XLA, SparseCore probes,
and execution across multiple hosts are subsequent extensions; their metadata
and capability boundaries belong in the initial architecture.

Preserve AMORA's evidence layers: published facts -> capabilities -> raw
observations -> normalized measurements -> TPU interpretations -> optional
consumer mappings. AMORA owns hardware evidence and workload definitions;
Accorde owns predictor fitting, PPP interpretation, and generalization gates.
The existing `amora benchmarks classify/detail` remain NVIDIA/GCoM pipelines;
TPU replay of CUDA-template `ppp_canonical` is outside this implementation scope.

## Architecture across generations

Separate three records; none is a substitute for another:

| Record | Stable contents | Qualification boundary |
|---|---|---|
| `ArchitectureProfile` | Versioned generation ID, variant, aliases, published architecture facts, units/scope, source revision, probe requirements/defaults | Describes hardware; published facts do not establish runtime or probe availability. |
| `RuntimeCompatibility` | Python/JAX/jaxlib/libtpu versions and wheel hashes, compiler APIs/options, supported-generation evidence, Pallas/profiler strategies | Each feature is qualified for an exact runtime/profile combination. Multiple locks may coexist. |
| `TargetInstance` | Instance ID, resolved profile, actual device/chip/core mapping, visible/addressable/global devices, host/process topology, memory exposure, ownership and environment digest | A qualification receipt applies to this configuration and records its runtime lock. |

The initial catalog includes `v2`, `v3`, `v4`, `v5e`, `v5p`, `v6e`, and
`tpu7x` (Ironwood). Keep exact generation/variant IDs: `v5e` and `v5p` are
different profiles, and aliases such as Trillium resolve to a sourced profile.
Catalog coverage expresses design coverage; hardware-supported status requires
an accepted qualification receipt. Older generations can use older supported
runtime locks. Future generations can be inventoried as `unknown` until a new
profile and compatibility evidence are added; do not infer capabilities from a
numeric generation comparison or silently use the nearest profile.

| Generation group | Structural differences to represent and verify |
|---|---|
| v2/v3 | Legacy runtime eligibility, device/chip/core modes, memory and fabric limits; Pallas availability is independently qualified. |
| v4 | Logical-device versus TensorCore/MXU mapping, core mode, local memory and fabric, optional SparseCore exposure. |
| v5e/v5p | Distinct products with independent geometry, memory, fabric, core modes and optional feature requirements. |
| v6e/tpu7x | New geometry, memory/fabric and compiler capabilities; SparseCore and profiling APIs remain explicit features. |
| Future/unknown | Preserve raw runtime identity; allow only operations whose runtime qualification succeeds and retain unresolved architecture facts. |

Record matrix tile geometry, vector layout, HBM/VMEM/SMEM capacity, supported
dtypes, DMA/semaphore facilities, SparseCore presence, and fabric topology with
the scope of each value: per chip, TPU TensorCore, MXU, logical device, or slice.
Unavailable values remain unknown. TPU TensorCore is Google's compute-core
term; MXU is a matrix unit within that architecture. Neither count is inferred
from JAX device count. Runtime core modes can change the device-to-core mapping.

Discovery resolves raw `device_kind` and, when available, the pinned runtime's
TPU-info APIs through a versioned alias resolver. Conflicts with provisioned
metadata or user-supplied profile selection are errors to investigate. Keep
raw values and provenance; PCI IDs are inventory hints. Feature gates combine
profile requirements, actual runtime APIs, compile-and-execute qualification,
and instance resources. Use capability states `unknown`, `declared`, `observed`,
`qualified`, and `unsupported`, with evidence/reasons for each feature. For
example, SparseCore declared by a profile does not mean SparseCore execution is
qualified. Probe implementations select a strategy by requirements; create a
generation-specific implementation only for demonstrated differences.

A hardware support matrix is keyed by profile revision × runtime lock × target
configuration × probe/feature. Qualification on one host establishes one row.
Synthetic fixtures for several generations test dispatch, units and degradation;
they do not establish measurements on those generations. Add each future host
through the same qualification workflow without changing the shared runner.

## Measurement and artifact contract

Each recipe fixes case/source hashes, input seed and digest, dtype/accumulation,
shape, profile revision, target/runtime identities, tile, sharding, compiler
flags, cache policy, warmup iteration count, measured sample count, timeout,
and device selection before execution. Declare the timed unit: one invocation
and drain for latency, or K back-to-back invocations and one drain for throughput.
Record K, retained outputs, input donation, output allocation/reuse/aliasing,
and buffer lifetimes. Donation invalidates inputs and requires an explicit
replenishment policy outside timing. Batching can still be host-dispatch-bound;
batch-duration/K is amortized time per invocation, not isolated device latency. A compiled
device loop is a separate realization with hoisting/elimination checks.

Every accepted timed run records device-holder/lock evidence and verified
exclusive use of its runtime/resource scope. `tpu:0` selects an array's logical
device; it does not guarantee that libtpu acquires only that device. Record the
runtime's acquired scope and any generation-specific visibility settings;
claim partitioned ownership only when verified. Other user directories indicate
a shared-host possibility, not proof of a concurrent TPU workload. Unverifiable
ownership produces diagnostic evidence rather than an accepted baseline.
Discovery must exit and release its resources before a bounded measurement
worker starts. Its timeout covers initialization, compilation, timing and
profiling; termination cleans up only the child/process group owned by that run.
Store a capability snapshot once and reference it from results.

1. **Prepare:** validate host inputs/static offsets and ranges, generate the CPU
   oracle, stage inputs, and complete all transfers before the execution lane.
2. **Compile:** construct a pure function with the frozen case/static metadata
   and dynamic array arguments. Lower and compile explicitly outside timing.
   Trace `case['nodes']` through a pure opcode dispatcher with validated
   `indices_validated`/`offsets_validated` attributes. Factor and share existing
   mathematical operation bodies where possible; keep generic adapter staging,
   `validate_inputs`, NumPy checks, host copies, and oracle calls outside JIT.
   Dynamic arguments must remain dynamic in jaxpr/HLO; verify changes to input
   values affect results without recompilation. Avoid closed-over input arrays
   or accidentally reusing an already computed output.
3. **Qualify:** check every output's shape, dtype, finiteness, and frozen numeric
   tolerances. Record tuple and empty outputs. Inspect generated code to establish
   the realized computation, fusion, padding, memory spaces, and sharding.
4. **Measure:** warm the same compiled executable for the declared iteration
   count, drain outstanding work, time the declared unit with `perf_counter_ns`,
   and block on every output leaf across all K invocations. Record raw
   samples, median/MAD, sample order, and host dispatch/completion overhead.
   Use observable, data-dependent outputs to prevent elimination or loop hoisting.
5. **Profile separately:** capture a repeat of the same executable and case;
   verify identities across lanes. Trace durations require documented device
   timestamps and a defined program/collective interval. Profiled latency is
   retained separately from the unprofiled execution series.

Name synchronized host timing `dispatch_to_completion_ns`; it includes dispatch
and completion overhead. Record compile, staging, first execution, warm execution,
profiling, process startup, and SSH/controller durations separately. Device-only
duration is available only when a validated trace exposes the required interval;
never convert host wall time into device cycles using an assumed clock.

Logical GEMM FLOPs and requested array bytes are derived workload quantities.
Rate = logical work / explicitly named time interval. Actual HBM traffic, MXU
utilization, and overlap require available profiler metrics or validated memory
and instruction paths. High-level JAX copies/transposes can be fused or removed;
Pallas makes a stronger controlled-memory probe possible but still needs code
inspection and observable output. Published peak values remain separate anchors.

Write new runs to `out/tpu/<recipe-id>/<recipe-digest>/<run-id>/`, with
`capabilities.json`, `recipe.json`, `manifest.json`, `correctness.json`,
`semantic-verification.json`, `samples.jsonl`, `report.json`, `compiler/`, and optional `profile/`. Manifests
hash all referenced artifacts, bind the source commit/dirty-source digest and
runtime lock, profile revision, target configuration and ownership receipt,
and record partial failures. Refuse existing run directories.
Compiler caches stay separate from evidence and are keyed by source, shape,
dtype, target generation/topology, compiler options, and runtime versions.
Curated family indexes use `reports/google_tpu/<verified-generation>/` and link
to immutable `<target-config-digest>/<runtime-lock-digest>/<run-id>/` reports.
Extend TPU report indexing to keep those identities; the existing renderer's
`manifest['skus'][sku]` overwrite must not merge distinct instances/runtimes.
Cross-generation comparisons require common workload/tolerance digests and
measurement units, retaining topology, per-chip/core scope and realization as
comparison axes. Raw evidence stays under ignored `out/` or a consumer-owned
artifact store.

### T0 — deploy and bootstrap an instance

Transfer a pinned source archive and SHA-256 manifest over the authorized SSH
route into an instance-owned checkout. This avoids assuming remote rsync or
private-repository credentials. Bind any intended dirty files explicitly;
verify the received source before installation. A clone or artifact-store
delivery can replace the archive if its source and authentication are recorded;
private keys/tokens are not copied into the checkout or evidence.

Record configured package indexes and verify artifact download/integrity, not
just an index response. This host's PyPI and libtpu-wheel HEAD checks pass;
that wheel was a connectivity probe and is not a Python/runtime compatibility
selection. Use an exact hash-checked wheelhouse if online resolution is
unavailable. Resolve a compatible lock on the host or qualify a supplied lock
against its Python ABI, target generation and runtime; the lock's origin alone
does not establish compatibility.

Refresh `sudo -n true` when performing setup and record the chosen method.
Default to a user-owned environment with a pinned bootstrap tool; available
sudo permits a targeted `python3-venv` installation if that is the selected
method. Docker-group changes are unnecessary for this runtime and are not a
prerequisite. The current ensurepip absence makes an unqualified
`python3 -m venv` recipe insufficient. Install AMORA's
`portable-core,test` extras and the official JAX TPU dependency set; resolve a
mutually compatible JAX/jaxlib/libtpu combination for the detected generation,
then lock exact versions and wheel hashes in an environment-specific receipt.
Do not require one newest lock to run every generation. Stable packages are
the initial choice; a necessary prerelease becomes an explicit compatibility decision.

Inventory the existing workload/ownership state before initializing TPU devices.
Use a bounded subprocess with `JAX_PLATFORMS=tpu` set before importing JAX;
missing TPU support must fail explicitly. Capture `jax.devices('tpu')`,
`jax.local_devices()`, process index/count, device kind, IDs, coordinates/core
metadata where exposed, and memory statistics where supported. Distinguish
global devices from locally addressable devices and logical cores from chips.
Compile a small vector operation and BF16 GEMM with FP32 output, block on both,
and check against a CPU oracle. Recreate a second clean environment from the
exact lock/wheel hashes and replay that smoke in T0. Save errors without
automatic runtime upgrades, device resets, or killing other workloads. This gate selects the actual family
and instance qualification row; hardware runtime failures do not become
successful CPU runs. The source/deployment, lock, ownership and smoke receipts
are prerequisites for accepted measurements on every later instance.

### T1/T2 — backend skeleton and portable workload admission

Add `tpu list`, `inspect-capabilities`, `run`, `measure`, and `report`. Probe
listing is static; inspection has separate package, hardware, runtime, compiler,
Pallas, profiler, and collective capability states. Define reasons such as
`runtime_missing`, `initialization_failed`, `initialization_timeout`,
`device_not_addressable`, `profile_unresolved`, `profile_conflict`,
`feature_unqualified`, and `profiling_unavailable`. Runtime errors and
correctness failures are preserved as failed measurements, not silently skipped.

Reuse the public portable package and its prepared semantic rules. For each
tier/profile, compare `base.core.digest(generate_cases(tier, profile))` and
the case count against `SEMANTIC_FINGERPRINTS.json`. `digest` computes SHA-256
over the ordered case-list JSON using sorted keys, compact separators and
`allow_nan=False`; this is distinct from the enclosing frozen-manifest digest.
The existing `test_case_fingerprints_preserve_upstream_contracts` already checks
all six entries. Reuse that procedure and store expected/actual digests and
counts in the run's `semantic-verification.json`, then bind the verified freeze receipt.
Run core20 first (152 smoke cases), then the 16 core24 and 16 core28 additions.
Use bounded shards with an aggregate coverage
receipt because the existing correctness CLI has a fixed 120-second whole-run
limit. Each case is either passed or explicitly failed/unavailable; incomplete
coverage cannot qualify a tier. Performance sweeps begin only on admitted cases.
Native-shape profiles are a subsequent bounded campaign with explicit memory
budgets. BF16 inputs, FP32 accumulation/output, gather bounds, deterministic
segment offsets, scatter initialization, and empty/tuple outputs keep their
existing mathematical contracts. Current frozen tolerances are the default.
For a genuine numerical difference, retain failing cases and quantify error
against independent high-precision/reference paths, including reduction or
duplicate-scatter ordering. First exclude implementation bugs and unintended
precision changes. A justified change requires an explicit versioned tolerance
policy, family/dtype/generation scope, evidence and rationale, and a new frozen
receipt; rerun affected and regression cases. Never rewrite old passes or use
the changed tolerance silently in cross-generation comparisons.

Compiler fusion and node materialization are execution-realization metadata;
the portable definitions alone do not prove them. Preserve imported Apache
notices and semantic fingerprints. Any adapter change that affects runtime
source hashes requires a new freeze receipt, with old snapshots retained.

### T3/T4 — initial probe registry

Required initial probes are topology metadata, dispatch latency, matrix
throughput, vector throughput and host/device transfer. Dependent-chain,
controlled HBM/local-memory, profiler and collective features qualify separately
per profile/runtime/instance; absence does not manufacture a successful result.

| Probe ID | Implementation and sweep | Admissible initial conclusion |
|---|---|---|
| `topology.device_attributes` | PJRT device kind, IDs, local/global ownership, coordinates, exposed memory statistics | Direct runtime metadata; missing attributes remain unknown. |
| `runtime.dispatch_latency` | Minimal observable JIT computation; invocation and completion series; compile/cache controls | Dispatch-to-completion behavior, with a minimum-work control. |
| `matrix.matmul_throughput` | BF16/FP32 and qualified dtype variants; aligned/tail M/N/K relative to sourced profile geometry; JAX then qualified Pallas tile sweep | Effective logical FLOP/s, realized lowering, padding and shape sensitivity; MXU claims require supporting evidence. |
| `matrix.dependent_chain` | Bounded data-dependent matrix chain with retained outputs and code checks | Compiled-program scaling; instruction latency only if a later probe isolates it. |
| `vector.elementwise_throughput` | Data-dependent FP32 arithmetic/reduction sweeps and materialized output | Effective vector program throughput; distinguish fusion and reduction. |
| `transfer.host_device` | Fresh observable H2D/D2H copies, preallocated controls, size sweep | Transfer completion cost and effective bandwidth; distinct from HBM traffic. |
| `global_memory.streaming` | Qualified Pallas HBM↔VMEM streaming with explicit read/write counts, profile-bounded working sets/tiles and buffer rotation | Effective controlled-transfer bandwidth; physical traffic needs counters. |
| `local_memory.transfer_sweep` | Capability-gated Pallas VMEM/SMEM/DMA/semaphore fixtures | Tile/transfer/synchronization curves; no assumed NVIDIA shared-memory/cache mapping. |
| `interconnect.collectives` | `shard_map` over an explicit mesh: `lax.psum`, `lax.all_gather`, `lax.ppermute`; payload/device-count/routing sweeps | Collective latency/effective bandwidth under the exact topology and realized algorithm. |

Require Pallas/Mosaic compile-and-execute qualification for each
profile/runtime/instance before claiming its probes are available;
interpretation/emulation results do not count
as TPU hardware evidence. Pair JAX and Pallas variants on common semantic inputs,
while preserving their different compiled realizations. Freeze sample counts
and quality thresholds before collection: initially 5 warmup iterations followed
by at least 30 measured samples per repeat, three independent repeats, and
relative MAD ≤5% for throughput curves. Profile/runtime/case-specific departures
must be justified and frozen before opening timing results. Mark noisy
curves inconclusive and retain samples; do not discard inconvenient repeats or
silently raise thresholds. Tiny dispatch probes report distributions rather than
an unjustified steady-throughput threshold.

Collectives start only after local addressability and topology are verified.
Bound working sets by available memory, validate sharding and participant outputs,
drain all participants, and prevent concurrent campaigns from sharing devices.
Record whether timings cover one collective or the whole compiled program;
algorithm changes and compute/communication overlap remain separate experiments.
Multiple-host rendezvous and SparseCore execution need their own admission gates.
Use the `shard_map` entrypoint available in the pinned JAX release, or `jit`
with `NamedSharding` for compiler-managed sharding; record which API and
collective primitives were actually compiled. Capability-gate mesh sizes,
intra-device core programming, local memory budgets and metric resolvers by
the exact profile/runtime. No probe copies the first host's eight-device
assumption or tile defaults into another generation.

### T5 — validation and documentation

selection, lazy imports, recipe validation, artifact tampering, overwrite
refusal, partial coverage, tuple synchronization, and time-domain labeling.
Use fake asynchronous workers with observably delayed completion to validate
the measurement boundary. Add selective `tpu`, `tpu_profile`, and `tpu_pallas`
markers; collect CPU tests without initializing libtpu. Test the existing NVIDIA,
GCoM, materialization, report, and portable-core contracts as regressions.
TPU runtime probes belong in session fixtures requested only by selected TPU
hardware tests, using the bounded worker; TPU marker registration and collection
must not import JAX. Include synthetic fixtures for v2/v3, v4, v5e, v5p,
v6e/tpu7x, conflicting identities and an unknown future generation. Validate
per-chip versus per-core units, runtime core-mode mappings, profile/package
data, feature degradation, and generation/runtime report separation.

Real-host checks qualify TPU JIT correctness, the 184 smoke cases, repeated
